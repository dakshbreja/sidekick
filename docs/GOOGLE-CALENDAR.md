Implementation checkpoint, October 12, 2026. This is an unfinished connector. The default website reports Google authorization and background collection unavailable. Authorization routes and UI are now implemented behind a disabled configuration gate. No live Google request, OAuth client, credential, source selection or alarm is enabled by this checkpoint.

## Implemented building blocks

`src/google-calendar.js` is a server-only read transport for calendar choices and event collection pages. It requests at most 100 items per page, reads at most 1 MB, applies a ten-second network/body deadline, rejects redirects, sends the access credential only in the Authorization header, and returns static error categories without provider payloads. It never follows arbitrary URLs, automatically retries, writes calendar events, chooses a student's calendars, or claims successful durable storage.

The connector consent scopes are `calendar.calendarlist.readonly` and `calendar.events.readonly`. These permit reading accessible calendars, not just calendars selected in our UI. The app must explain that distinction and collect only the selected IDs after consent. [Google's scope documentation](https://developers.google.com/workspace/calendar/api/auth).

Full and incremental event requests use the same fixed query parameters, preserve cancelled events and retain recurrence masters/original occurrence identities. Each call returns one page. A continuation is explicitly incomplete; only a final page supplies the next sync token. The adapter reports `recurrence_expanded: false`, so these objects cannot be presented as a fully expanded upcoming schedule. [Google synchronization contract](https://developers.google.com/workspace/calendar/api/guides/sync), [event list restrictions](https://developers.google.com/workspace/calendar/api/v3/reference/events/list).

401 requires token refresh before considering a new consent prompt. 410 on incremental collection requires a new full sync. Rate limits and server failures are separately retryable; remaining failures stop collection. A durable scheduler must honor Retry-After and exponential backoff. Errors do not overwrite the last successful collection time. [Google error guidance](https://developers.google.com/workspace/calendar/api/guides/errors).

`src/credential-envelope.js` supplies versioned AES-256-GCM encryption with random 96-bit IVs and authenticated student, connection, generation and purpose context. It rejects altered ciphertext, another student's context, another connection/generation/purpose, malformed keys and oversized plaintext. The encryption secret must be community-only and separate from the workspace-addressing key. This is server-side encryption at rest, not end-to-end encryption; key rotation is not implemented yet. The private live-row lifecycle is described below.

The new tests use only generated keys and synthetic provider responses. One integration test executes both components in actual local workerd and intercepts outbound HTTP, preventing live Google access. These transport tests do not establish provider authorization, scheduled refresh or live correctness.

## Durable authorization state, October 12

`src/google-connection-state.js` now implements internal, per-student authorization state in the same SQLite database as the workspace. The state table is separate from normal records, receipts and exports. The schema upgrade is idempotent; account deletion clears private connector rows atomically with the existing tombstone. Every state mutation also advances the account revision, so stale account-deletion requests must reread first.

An authorization attempt stores encrypted state/PKCE verifier/redirect data, hashes the browser binding, expires after ten minutes, and can return the original intent on an exact retry after restart. A different browser, owner, callback state or changed request cannot reuse it. The callback consumes the pending state before decryption or provider exchange and grants a one-minute internal exchange lease. A lost/ambiguous exchange is not replayed; start a new attempt. After a successful final save whose response is lost, read connection status instead of exchanging the code again.

Credential commits recheck the lease, generation, expiry and account tombstone after encryption. Disconnect persists a generation fence even if the first authorization is still awaiting encryption. It erases live local credentials and pending secrets, and reports provider revocation as **not attempted**. Reauthorization of an existing authorized connection requires explicit disconnect first. The state is bounded to eight registered Google connections and 40 KB per private row. Expired pending ciphertext remains bounded until a new attempt, disconnect or account deletion; it cannot be consumed after expiry.

A successful synthetic credential save reports `authorized_not_synced`, never successful collection. The internal class must not be exposed wholesale: its consume method returns a PKCE verifier exclusively for trusted server-side exchange. The narrow server wrapper described below keeps that verifier, exchange leases and credentials inside the student object. The state component itself does not perform network requests or set cookies.

Sixteen added tests cover real SQLite close/reopen, exact retry, callback reuse, competing calls, expiry, owner/browser/state mismatch, contextual encryption, input/connection limits, rollback, generic-dispatch exclusion, and disconnect/deletion while encryption is paused. A separate real workerd/SQLite test restarts the runtime across pending, consumed, authorized and deleted states and blocks all external HTTP. These are synthetic lifecycle tests, not live Google consent or hosted deletion evidence. Live-row erasure also does not establish erasure from provider grants or infrastructure backups; revocation, restore handling and retention remain release gates.

## Authenticated consent routes and UI, October 12

The opt-in website flow now has prepare, begin, status, callback and local-disconnect routes. All derive the student from the existing verified assertion. New mutation routes additionally require the exact configured Origin and initiating workspace header. Prepare installs a ten-minute HttpOnly/Secure/SameSite=Lax host cookie; begin requires that cookie and a registered Google source. Exact begin retries return the same consent URL. Multiple callbacks for different sources can share the browser binding, but each state is separately connection- and student-bound.

The consent URL pins Google's endpoint, the two read-only scopes, offline access, an account chooser and a consent prompt, with PKCE S256. The callback validates its state, browser binding and optional issuer before a single server-side code exchange. Exchange uses a fixed token endpoint, POST body credentials, no redirects, a ten-second deadline and a 32 KB response ceiling. It checks token type, both exact scopes, refresh-token presence and expiry, preserving optional refresh expiry. Provider payloads never appear in errors. Denials and uncertain exchanges are recorded as unsuccessful; browser refresh cannot reuse the consumed code.

Callbacks always redirect to a fixed local page with a generic result marker, clearing provider codes/state from the visible URL. The UI removes the marker, rereads authoritative status, and distinguishes authorization from collection. The consent checkbox explains the scope-versus-selection distinction. Removal explicitly erases saved access locally without claiming provider revocation. The browser holds no provider credential or PKCE verifier. Exact retry remains possible while the initiating page/cookie survives; after browser state is lost, reread status and explicitly start a new attempt rather than guessing a previous result.

Enablement requires `GOOGLE_OAUTH_ENABLED=true`, a separate community `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, an exact HTTPS `GOOGLE_REDIRECT_URI` ending in `/api/google/callback`, and a 256-bit canonical base64url `GOOGLE_CREDENTIAL_KEY` distinct from `TENANT_ID_KEY`. Defaults stay disabled. Do not copy the personal Bridge registration or credentials. The default Wrangler configuration now redacts query strings, disables invocation logs and disables tracing; apply and independently verify equivalent settings in the protected deployment configuration before live consent. Access and other infrastructure logging/retention must also be reviewed; source configuration alone is not proof of live redaction.

New controlled HTTP tests run the actual Worker and SQLite with synthetic signed identities and intercepted provider traffic. They cover normal consent, PKCE correspondence, exact begin replay, foreign identity/cookie/state, CSRF/workspace checks, denied/ambiguous responses, and disconnect/account deletion during provider exchange. Transport tests cover malformed permissions, expiry, bounded/stalled responses and no automatic retry. The rendered UI test uses synthetic route responses to check consent wording, checkbox enforcement, pinned navigation and truthful status/removal; it is not a live Google browser test. Actual web-client PKCE enforcement, consent, redirect admission through Access and end-to-end live behavior remain unverified until an approved separate client is configured.

## Durable refresh and calendar discovery, October 12

Calendar-list reads now acquire access through `src/google-access.js`. A near-expiry access token triggers one persisted per-connection refresh lease before any network call. The lease survives restart; competing calls receive a retryable wait. Expired leases can be replaced, but older completions cannot overwrite the replacement or a newer credential revision. Refresh results are encrypted and committed before use. Tokens, refresh claims and leases remain inside the student object and never cross the RPC or HTTP boundary.

A refresh response may omit its refresh token or scope; in that case the previously verified values are preserved. An explicit replacement is validated and stored. Known refresh expiry is retained and enforced. Provider `invalid_grant`, reduced scopes, or a second 401 after refresh erase live credentials and require new consent. Temporary failures preserve credentials and persist exponential backoff with jitter and Retry-After; invalid-client responses back off for at least an hour. Refresh never advances a collection timestamp. A lost response after provider-side token rotation may still require reauthorization if the previous token is no longer usable; these checks cannot guarantee perpetual access.

Calendar discovery makes at most two list requests and one refresh per operation. A 401 is associated with the exact token revision that failed, so a concurrently renewed credential can be reused. Responses are rechecked against the current authorization generation before leaving the student object; disconnect or account deletion discards late provider data. Malformed cursors are rejected before refresh or external access.

The optional source UI now displays refresh/retry/reauthorization states and a **Show Google calendars** preview. It reads one bounded page per click, renders names literally, detects repeated cursors, and stops at ten pages while clearly labeling an incomplete list. Discovery returns the latest connection revision so subsequent removal does not use a revision made stale by refresh. Calendar names are choices only: selection, event collection and successful-sync timestamps are not enabled by this preview.

Fifteen added tests cover omitted/rotated refresh-token behavior, preserved scopes/expiry, Retry-After, competing leases, restart/expired-lease recovery, stale commit rejection, transient/revoked responses, and disconnect/deletion. Actual Worker/SQLite HTTP tests exercise near-expiry refresh, 401 retry limits, persistence across full runtime restarts, two-identity isolation and late provider-response rejection. All provider responses are synthetic. The browser suite previews two pages of calendar choices and literal script-looking names using route mocks. This establishes controlled behavior, not live Google reliability or unattended collection.

## Durable calendar selections

Authenticated discovery caches only provider-observed calendar IDs and names in the same student database, bound to the current authorization generation. The private cache expires during subsequent discovery and is capped at 1,000 choices / 1 MB per workspace. It is excluded from exports and removed on disconnect, invalidation or workspace deletion. Cache writes do not claim a successful source sync or advance the user's saved-work revision.

The opt-in website lets the student select at most 20 calendars per connection and explicitly save or clear that selection. New selections require discovery within the previous hour. Retained choices can be removed without repeating discovery. The selection, source-derived names and normal operation receipt commit atomically; exact retries work even after discovery expires. Selected names are included in workspace exports. The selection is inactive after the authorization generation changes and never silently follows a different Google account.

The source gate passes 239 tests, including SQLite rollback, stale discovery, forged IDs, owner isolation, cache limits, disconnect/reauthorization, real authenticated Worker routes and full runtime restart. The rendered suite adds explicit checkbox selection, reload after a dropped save response, receipt-only recovery without another write, and draft-only clear followed by an explicit empty save. Those browser provider routes are synthetic; no Google account has been connected.

### Terminal selection recovery

A validated selection rejected because its authorization changed, its revision became stale, or its new choices lack recent discovery now receives a permanent `outcome: rejected` receipt. The receipt and account revision commit atomically without changing the selected-calendar record or its revision. The original operation ID and normalized request hash are reserved: retries return the same rejection even after reconnect or fresh discovery, while a corrected choice requires a new operation. Previously successful receipts always win and cannot become rejections.

Receipt-first browser recovery distinguishes saved and rejected outcomes. It clears an uncertain selection only after verifying the rejection's exact normalized request hash, operation, resource, expected revision and allowed reason. An error alone, missing receipt, mismatched evidence, authentication failure, conflicting prior success acknowledgement or failed local cleanup retains the pending packet. The interface explicitly says the selection was not saved and asks the student to review current choices.

Eight additional tests cover permanent rejection/replay, concurrent stale copies, SQL rollback after receipt insertion, browser restart, missing/mismatched evidence and cleanup failure. The actual authenticated Worker test loses both the original request and the later rejection reply across two complete runtime restarts; receipt-only recovery clears the correct owner's outbox, leaves the selection absent, and rejects another owner's receipt query. The full local gate passes 247 tests. The rendered browser suite also reproduces interrupted selection followed by disconnect and checks the not-saved message. This resolves the earlier pending-selection gap for these three terminal preconditions; general outages remain recoverable pending states. No live provider or deployment changed.

## Staged event collection engine

`src/google-collection-state.js` and `src/google-collector.js` implement an internal one-page collection step. They are not yet invoked by website routes or alarms. The schema migration adds private run metadata, temporary event rows, published event rows and hashed page history in the student's existing SQLite database. Only completed, currently selected and authorized snapshots enter `google_calendar_snapshots` in workspace export; credentials, leases, provider cursors and unfinished pages are excluded.

A run holds a 60-second lease and pins the authorization generation, selection revision, run ID, page number and base sync token. Every provider attempt checks that the selection still applies. Commit repeats the checks after network/crypto work. Expired leases resume the same page, and old responses cannot overwrite a replacement lease. Incremental runs seed temporary storage from the last published snapshot and keep one base sync token through all pages. Repeated page cursors stop collection. Final publication replaces the source event set, advances its cursor, records the successful-check time and increments the account revision in one synchronous transaction. Intermediate pages do not advance the account revision or successful-check time.

Ordinary retries preserve the previous snapshot and the staged continuation. Transient failures use persisted exponential backoff with jitter and full Retry-After; eight failures pause a run. A run older than 24 hours restarts staging from the last published cursor. An invalid sync token clears that source's old data/cursor before a full rebuild because Google may also invalidate tokens after access changes. Permission loss clears the source and pauses it. [Google synchronization contract](https://developers.google.com/workspace/calendar/api/guides/sync).

Changed selection cancels in-flight pages and removes deselected source data; unchanged selected sources retain their published snapshot. Disconnect, credential invalidation and workspace deletion clear the connection's run, temporary and published rows in their existing transaction. Fault tests verify rollback across these lifecycle changes and final publication.

Bounds are 500 pages per run, 10,000 records per calendar, and 20,000 records / 8 MB per workspace **in each** of published and temporary storage. These include cancellation records. Competing temporary-copy reservations wait with persisted retry timing and an eight-attempt ceiling. An over-limit page/publication stops without pretending its results are complete. These are explicit limits, not measured capacity or cost guarantees. A future scheduler must additionally enforce request budgets and fair admission.

Snapshots retain raw recurrence masters and cancellation exceptions, original all-day dates and time zones; `recurrence_expanded` remains false. They are not yet an upcoming-event schedule. Paginated snapshot reads require the opaque snapshot ID captured on the first page. A replaced or removed/recreated snapshot rejects an old continuation even when its numeric revision happens to match. Status distinguishes never-synced, recent and stale data, with collection/backoff/paused states.

Seventeen new synthetic checks cover atomic publication/rollback, stable incremental cursors, duplicate IDs, cancellations, abandoned leases, source changes before/during provider access, deletion and owner isolation, quotas, page loops, terminal failures and snapshot identity. Three use real workerd/SQLite with intercepted Google responses, full restarts, throttling, 410 reset and in-flight disconnect. The engine has no live provider access and no scheduler yet; browser rendering still verifies the currently available consent/selection/import/recovery controls.
